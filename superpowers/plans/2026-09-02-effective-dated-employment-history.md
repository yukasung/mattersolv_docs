# Effective-Dated Employment History Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add tenant-safe, effective-dated employment history based on Odoo 19 `hr.version`, while retaining a synchronized current employment snapshot on `employees`.

**Architecture:** `employee_employment_versions` is the source of truth for past, current, and future employment assignments. `employees` keeps a current projection for existing frontend and list-query compatibility; composite tenant foreign keys, partial uniqueness, RLS, and deferred PostgreSQL triggers protect the projection, while future Django services will provide row locking, tenant-local date selection, lazy refresh, scheduled activation, and audit orchestration.

**Tech Stack:** PostgreSQL 18, drawDB JSON (`database.ddb`), Node.js static verifiers, `psql` runtime verification, Nextra documentation.

## Global Constraints

- Work in the current `docs` repository and execute inline; do not create a worktree or dispatch subagents.
- PostgreSQL 18 is the schema target.
- MatterSolv-owned tables use `BIGINT GENERATED BY DEFAULT AS IDENTITY` internally and UUID v7 `public_id` externally.
- Every tenant-owned relationship uses a composite tenant foreign key and the verified internal `app.tenant_id BIGINT` RLS context.
- `employee_employment_versions` is the source of truth; cached current fields on `employees` must match its selected current version exactly, including null values.
- Employment versions contain employment assignment data only; personal, contact, identity, private, and payroll data stay on their existing owners.
- Current selection uses the server-derived business date in `tenants.timezone`: latest active `effective_from <= business_date`, otherwise earliest active future version.
- Version state is derived; do not add persisted `past`, `current`, `future`, or `effective_to` columns.
- Employment history is append-preserving: runtime roles can select, insert, and update but cannot hard-delete versions.
- Keep the existing frontend employee response fields; no frontend component or fixture changes are required by this schema-only phase.
- The workspace has no Django backend yet. Document scheduled activation, lazy refresh, transaction locking, audit, and temporal cycle validation as required backend contracts; do not create placeholder backend code.
- Preserve and do not stage unrelated user-owned changes already present in the worktree.

```sql
    p_tenant_id bigint,
    p_employee_id bigint,
    p_business_date date
```

Add this complete deferred validation function. Both installed triggers handle `INSERT` and `UPDATE`, so `NEW` always identifies the affected employee:

```sql
CREATE OR REPLACE FUNCTION validate_employee_employment_snapshot()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
    affected_tenant_id bigint;
    affected_employee_id bigint;
    business_date date;
    selected_version_id bigint;
    employee_row employees%ROWTYPE;
    version_row employee_employment_versions%ROWTYPE;
BEGIN
    IF TG_TABLE_NAME = 'employees' THEN
        affected_tenant_id := NEW.tenant_id;
        affected_employee_id := NEW.id;
    ELSE
        affected_tenant_id := NEW.tenant_id;
        affected_employee_id := NEW.employee_id;
    END IF;

    SELECT (CURRENT_TIMESTAMP AT TIME ZONE tenant.timezone)::date
    INTO STRICT business_date
    FROM tenants AS tenant
    WHERE tenant.id = affected_tenant_id;

    SELECT * INTO STRICT employee_row
    FROM employees
    WHERE tenant_id = affected_tenant_id AND id = affected_employee_id;

    selected_version_id := select_employee_employment_version(
        affected_tenant_id,
        affected_employee_id,
        business_date
    );
    IF selected_version_id IS NULL THEN
        RAISE EXCEPTION 'employee must have an active employment version'
            USING ERRCODE = '23514';
    END IF;

    SELECT * INTO STRICT version_row
    FROM employee_employment_versions
    WHERE tenant_id = affected_tenant_id
      AND employee_id = affected_employee_id
      AND id = selected_version_id;

    IF employee_row.current_employment_version_id IS DISTINCT FROM version_row.id
       OR employee_row.department_id IS DISTINCT FROM version_row.department_id
       OR employee_row.job_position_id IS DISTINCT FROM version_row.job_position_id
       OR employee_row.manager_employee_id IS DISTINCT FROM version_row.manager_employee_id
       OR employee_row.employment_type IS DISTINCT FROM version_row.employment_type
       OR employee_row.contract_start_date IS DISTINCT FROM version_row.contract_start_date
       OR employee_row.contract_end_date IS DISTINCT FROM version_row.contract_end_date THEN
        RAISE EXCEPTION 'employee current employment snapshot is inconsistent'
            USING ERRCODE = '23514';
    END IF;
    RETURN NEW;
END;
$$;
```

Install both deferred triggers:


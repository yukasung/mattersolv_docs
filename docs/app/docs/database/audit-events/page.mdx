# Audit Events

`audit_events` เก็บหลักฐานว่าใครทำอะไรกับข้อมูลใดในสำนักงานใดเมื่อไร หน้านี้รวม
กติกาการใช้งานที่กระจายอยู่หลายที่ให้มาอยู่ที่เดียว โครงสร้างคอลัมน์และข้อจำกัด
ในฐานข้อมูลอยู่ที่ [Tenant & Authorization](/docs/database/tenant-authorization)
ส่วนเหตุผลของการเลือกรูปแบบนี้อยู่ใน ADR-001

สำหรับสำนักงานกฎหมาย บันทึกนี้คือสิ่งที่ตอบได้ว่าใครแก้ค่าธรรมเนียมในแฟ้มงาน
สัญญา ใครส่งออกรายชื่อลูกความ และใครเปลี่ยนสิทธิ์ให้ทนายคนหนึ่งเห็นแฟ้มคดีแรงงาน
ที่ไม่ใช่ของตัวเอง

## เขียนแล้วแก้ไม่ได้

ตารางนี้มี policy เฉพาะ `SELECT` และ `INSERT` ไม่มี `UPDATE` และ `DELETE`
ภายใต้ `FORCE ROW LEVEL SECURITY` การเขียนผิดจึงลบทิ้งไม่ได้และแก้ไม่ได้
`verify-database-tenant-isolation.mjs` ตรวจไว้ด้วยว่าห้ามมีใครเพิ่มสอง policy
นั้นเข้ามาภายหลัง

ผลที่ตามมาซึ่งต้องคิดก่อนเขียนเสมอ คือทุกอย่างที่ใส่ลงไปจะอยู่ถาวร รวมถึงข้อมูล
ส่วนบุคคลที่เผลอใส่ลงไปด้วย

## กติกาที่ต้องทำตาม

### ต้องเขียน audit เมื่อใด

กฎหลักอยู่ที่ [Permissions](/docs/roles/permissions) — การลบ ส่งออก อนุมัติ
เปลี่ยนสิทธิ์ และแก้ข้อมูลการเงินต้องสร้าง audit event ทุกครั้ง และ
[Database](/docs/database) กำหนดกว้างกว่านั้นว่าการเปลี่ยนแปลงข้อมูลสำคัญต้อง
สร้าง audit record ที่แก้ย้อนหลังไม่ได้

### ต้องอยู่ใน transaction เดียวกับการเปลี่ยนข้อมูล

ห้ามเขียนแบบ best-effort และห้ามยิงแบบ fire-and-forget ไปทำทีหลัง ถ้าการเขียน
audit ล้มเหลว การเปลี่ยนข้อมูลต้องล้มเหลวตามไปด้วย เพราะข้อมูลที่เปลี่ยนแล้ว
โดยไม่มีร่องรอยแย่กว่าการที่คำสั่งนั้นไม่สำเร็จตั้งแต่แรก

### actor ที่เป็น NULL หมายถึงระบบเท่านั้น

`actor_tenant_user_id` เป็น NULL ได้เฉพาะเมื่อระบบเป็นผู้ทำจริง เช่น scheduled
job หรือ migration **ห้ามใช้แทนความหมายว่า "ไม่รู้ว่าใครทำ"** ถ้าโค้ดหาผู้กระทำ
ไม่เจอ ให้ถือว่าเป็นข้อผิดพลาดแล้วหยุด ไม่ใช่บันทึกเป็น NULL

action ที่ registry ระบุ `requiresActor` ห้ามเป็น NULL ทุกกรณี

### request_id ร้อยเหตุการณ์ที่มาจากคำสั่งเดียวกัน

`request_id` มาจาก middleware ระดับ request หนึ่งค่าต่อหนึ่ง HTTP request คำสั่ง
เดียวที่กระทบหลายตารางจะได้ค่าเดียวกันทุกแถว ทำให้ไล่ย้อนได้ว่าเหตุการณ์เหล่านั้น
เกิดจากการกระทำครั้งเดียว

### ต้องบันทึกสิทธิ์ที่ใช้ตัดสิน ณ เวลานั้น

[Development Rules](/docs/development/rules) กำหนดว่าต้องบันทึกสิทธิ์ที่ใช้
ตัดสินลง audit เพราะบทบาทแก้ไขภายหลังได้ การเก็บเพียงชื่อกลุ่มจึงพิสูจน์ย้อนหลัง
ไม่ได้ ให้เก็บรายการ permission ที่ใช้อนุญาตไว้ใน `after_data` ภายใต้คีย์
`granted_permissions`

### ข้อมูลอ่อนไหวต้องปกปิดก่อนเขียน

`docs/scripts/audit-event-contract.mjs` ระบุคอลัมน์ที่ห้ามบันทึกค่าดิบ ปัจจุบันคือ
`employees.identity_number` และ `employees.identity_number_key` (เลขบัตรประชาชน)
ให้เก็บเป็นค่าที่ปกปิดแล้วหรือ hash

เหตุผลที่ต้องกำหนดตั้งแต่ยังไม่มีข้อมูลจริง คือตารางนี้ลบไม่ได้ ถ้าปล่อยให้เลข
บัตรประชาชนไหลลงไปแล้วจะเอาออกไม่ได้อีกเลย

## แบบแผนการตั้งชื่อ

| คอลัมน์ | รูปแบบ | ตัวอย่าง |
| --- | --- | --- |
| `action` | `<domain>.<verb_phrase>` โดย verb เป็นอดีตกาล | `tenant.number_format_changed` |
| `entity_type` | ชื่อตารางรูปเอกพจน์ | `tenant_number_sequence` |

ทั้งสองค่าต้องจดทะเบียนไว้ใน `docs/scripts/audit-event-contract.mjs` และ
`verify-database-audit-events.mjs` ตรวจว่า domain ถูกประกาศไว้ verb เป็นอดีตกาล
และ `entity_type` ตรงกับชื่อตารางที่มีอยู่จริงในไดอะแกรม

กติกานี้อยู่ใน registry ไม่ใช่ CHECK constraint เพราะการเพิ่ม action ใหม่ควรเป็น
การแก้โค้ด ไม่ใช่การทำ migration ทุกครั้ง ใช้แนวเดียวกับที่คุมความยาว string อยู่แล้ว

## เส้นแบ่งกับตาราง history แบบ typed

`employee_employment_versions` ไม่ใช่ audit log แต่เป็น source of truth ของข้อมูล
การจ้างงานที่มีผลตามช่วงเวลา ใช้เกณฑ์นี้แยก

- ถ้าแอปต้องอ่านย้อนหลังเพื่อตอบคำถามเชิงธุรกิจ เช่น "วันที่ 1 มกราคม พนักงาน
  คนนี้อยู่แผนกใด" ให้ทำเป็นตาราง typed ที่มีคอลัมน์และ constraint ชัดเจน
- ถ้าเป็นหลักฐานว่าใครทำอะไร ให้ใช้ `audit_events`
- **การแก้ข้อมูลในตาราง typed ต้องเขียน `audit_events` ควบคู่เสมอ** ไม่ใช่เลือก
  อย่างใดอย่างหนึ่ง

ความต่างนี้สะท้อนใน RLS ด้วย ตาราง history แบบ typed แก้ไขได้ (`UPDATE` เพื่อ
ตั้ง `is_active = false`) ส่วน `audit_events` เขียนเพิ่มได้อย่างเดียว

## ยังไม่ตัดสินใจ

เรื่องต่อไปนี้ยังไม่มีข้อสรุป และระบุตัวขวางไว้เพื่อไม่ให้เข้าใจผิดว่าลืม

| เรื่อง | ตัวขวาง |
| --- | --- |
| ระยะเวลาเก็บ | ไม่มีตัวเลขกำหนดไว้ที่ใดเลย เอกสารให้ขึ้นกับนโยบายสำนักงานและระยะเวลาที่กฎหมายกำหนด ส่วน PDPA ยังไม่ได้รับอนุมัติให้เปิดใช้ในรอบนี้ |
| ใครดู log ย้อนหลังได้ | มีเพียง permission `audit.audit_log` และ `audit.export_audit_log` ยังไม่มี spec หน้าจอสำหรับดูหรือค้นหา |
| module ใดต้อง audit บ้าง | นอกจากกฎกลางแล้ว Clients, Matters, Time tracking และ Billing ยังไม่มีข้อกำหนดเฉพาะ |
| audit การอ่านข้อมูล | ข้อกำหนดของ Documents ต้องการบันทึกประวัติการเข้าถึงไฟล์ แต่ปริมาณต่างจาก audit การเขียนมาก ยังไม่ตัดสินว่าใช้ตารางเดียวกันหรือแยก |
| เก็บ IP ผู้กระทำหรือไม่ | ยังไม่มีข้อกำหนด ถ้าจะเพิ่มควรเพิ่มก่อนมีข้อมูลจริง |
| Partitioning | [Database](/docs/database) กำหนดให้วัดขนาดและ query plan ก่อน ยังไม่มีข้อมูลปริมาณ |

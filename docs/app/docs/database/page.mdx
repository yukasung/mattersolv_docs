# Database

ระบบใช้ Cloud SQL for PostgreSQL เป็นฐานข้อมูลหลัก ข้อมูลธุรกิจต้องแยกตาม
Workspace และต้องตรวจสอบย้อนหลังได้ การออกแบบฐานข้อมูลต้องใช้ร่วมกับ
Authentication, Permission และกฎใน Development Rules

## Database Principles

- ใช้ PostgreSQL เป็นแหล่งข้อมูลหลักของรายการธุรกิจ
- ทุกตารางที่เป็นของบริษัทต้องมี `workspace_id` และ foreign key ที่ถูกต้อง
- เงิน จำนวน เวลา สถานะ และข้อมูลที่ใช้อนุมัติต้องใช้ชนิดข้อมูลกับ constraint
  ที่ชัดเจน
- ใช้ `VARCHAR(n)` เมื่อมีเพดานจาก requirement, frontend หรือมาตรฐานภายนอก
  ที่ยืนยันได้ เช่น login email, country/currency code, employee input และที่อยู่
  ส่วนข้อความที่ไม่มีเพดานชัดเจนให้ใช้ `TEXT` โดยไม่กำหนด `VARCHAR(255)` ขึ้นเอง
- เอกสารจริงเก็บใน Cloud Storage ส่วน metadata, version และ permission เก็บใน
  PostgreSQL
- การเปลี่ยนแปลงข้อมูลสำคัญต้องสร้าง audit record ที่แก้ย้อนหลังไม่ได้
- Migration ต้องรองรับข้อมูลเดิมและมีวิธีตรวจสอบผลก่อนเปิดใช้ production

## Workspace Isolation

ทุก query ของข้อมูลธุรกิจต้องจำกัดด้วย Workspace ที่ตรวจสอบจากผู้ใช้หรือ system
identity ฝั่ง server ห้ามเชื่อถือ `workspace_id`, `company_id` หรือ `user_id`
ที่ส่งมาจาก request โดยตรง

- ใช้ Django QuerySet หรือ service กลางบังคับ `workspace_id`
- ตรวจ Workspace กับรายการหลักและข้อมูลที่เกี่ยวข้องทุกครั้ง
- Aggregate, report, export, bulk operation และ background job ต้องใช้ขอบเขต
  Workspace เดียวกัน
- Unique constraint ของข้อมูลที่ไม่จำเป็นต้องซ้ำข้ามบริษัทควรรวม `workspace_id`
- ตารางข้อมูลกลางที่ไม่เป็นของสำนักงานต้องระบุเป็นข้อยกเว้นอย่างชัดเจน
  โดยตาราง Django auth เป็นข้อมูลกลางตามหัวข้อถัดไป

## Internal and Public Identifiers

ตารางที่ MatterSolv เป็นเจ้าของใช้ `id BIGINT GENERATED BY DEFAULT AS IDENTITY`
เป็น Primary Key และใช้เป็น Foreign Key สำหรับ join ภายในฐานข้อมูล ส่วน entity
ที่ส่งผ่าน API หรือ URL มี `public_id UUID NOT NULL UNIQUE DEFAULT uuidv7()`
เพิ่มอีกคอลัมน์หนึ่ง วิธีนี้ทำให้ join และ index มีขนาดเล็กลง แต่ยังไม่เปิดเผย
เลขลำดับภายในระบบให้ client เห็น

ตารางเชื่อมภายใน เช่น `tenant_groups`, `tenant_role_assignments`,
`plan_entitlements` และ `tenant_entitlement_overrides` ไม่มี `public_id`
เพราะ client ไม่ได้อ้างถึง record เหล่านี้โดยตรง ตาราง Django auth ยังคงใช้
`BIGINT` ตาม Django migrations

`X-Tenant-ID` ต้องเป็น `tenants.public_id` แบบ UUID เท่านั้น Backend ต้องค้นหา
`tenants.id` แบบ `BIGINT` ตรวจ active membership และสถานะ Workspace ก่อนตั้ง
`SET LOCAL app.tenant_id` ด้วยค่า internal ID ภายใน transaction Frontend ต้องมอง
identifier ทุกชนิดเป็น opaque string และห้ามพึ่งชนิดหรือลำดับของ `id`

## Django Roles and Permissions Tables

MatterSolv ใช้ Default Django User, `ModelBackend` และตารางมาตรฐานของ
`django.contrib.auth` เป็น contract หลัก โดยไม่สร้างระบบ User, Role หรือ Permission
ซ้ำอีกชุดหนึ่ง ตาราง Django สร้างโดย Django migrations ส่วนตารางเชื่อม tenant
เป็นของโดเมน MatterSolv

| ตาราง | ขอบเขต | คำอธิบาย |
| --- | :---: | --- |
| `auth_user` | ทั้งระบบ | บัญชีเข้าสู่ระบบมาตรฐานของ Django ใช้ `BIGINT` เป็น Primary Key |
| `auth_permission` | ทั้งระบบ | Django model permissions และ custom permissions ที่สร้างจาก migration |
| `auth_group` | ทั้งระบบ | กลุ่มสิทธิ์มาตรฐานของ Django; หนึ่งกลุ่มเป็นบทบาทของสำนักงานผ่านตารางเชื่อม |
| `auth_group_permissions` | ทั้งระบบ | ผูก Django Group กับ Django Permission |
| `auth_user_groups` | ทั้งระบบ | ใช้เฉพาะ Group ระดับระบบที่ไม่ขึ้นกับสำนักงาน; ไม่ใช้มอบบทบาทรายสำนักงาน |
| `auth_user_user_permissions` | ทั้งระบบ | ใช้เฉพาะ Permission ระดับระบบ; ไม่ใช้มอบสิทธิ์รายสำนักงาน |
| `tenant_groups` | รายสำนักงาน | ผูก `tenant_id` กับ `group_id` และเก็บ `code`, `display_name` |
| `tenant_role_assignments` | รายสำนักงาน | ผูกสมาชิกกับ `tenant_group_id`; ไม่เพิ่มบทบาทสำนักงานลง `auth_user_groups` |

Login Email ต้องผ่าน `lower(btrim(email))` และยาวไม่เกิน 150 ตัวอักษร ระบบบันทึก
ค่าเดียวกันใน `auth_user.username` และ `auth_user.email` เพื่อให้เข้าสู่ระบบด้วย
อีเมลผ่าน `ModelBackend` มาตรฐานโดยไม่สร้าง Custom User หรือ Authentication Backend
ข้อมูลเพิ่มเติม เช่น ชื่อที่แสดง โทรศัพท์ และเวลายืนยันอีเมลอยู่ใน `user_profiles`

กฎการใช้งาน:

- ตรวจว่าสมาชิกและ Django Group เชื่อมกับสำนักงานเดียวกันก่อนเพิ่มหรือลบสมาชิก
- ทุกการจัดการบทบาทต้อง query ผ่าน `tenant_groups` และ `tenant_role_assignments`
  เพื่อป้องกันการใช้ Group ข้ามสำนักงาน
- `auth_group.name` ใช้ชื่อภายในที่ unique ทั้งระบบ เช่น `<tenant_uuid>:<role_code>`
  ส่วนชื่อที่ผู้ใช้เห็นเก็บใน `tenant_groups.display_name`
- การสร้างสำนักงานใหม่คัดลอก role template เป็น `auth_group` ใหม่ แล้วเชื่อมกับสำนักงานใหม่
- สิทธิ์มาตรฐานและสิทธิ์พิเศษประกาศบน Django model และสร้างโดย migration เท่านั้น
- สิทธิ์ระดับระบบที่ไม่ขึ้นกับสำนักงานตรวจด้วย `user.has_perm()` ได้ตาม Django
- สิทธิ์ของบทบาทสำนักงานต้องตรวจด้วย `has_tenant_perm(user, tenant, permission)`
  ซึ่ง query `tenant_role_assignments -> tenant_groups -> auth_group_permissions`; ห้ามใช้
  `user.has_perm()` ตัดสินสิทธิ์รายสำนักงาน เพราะ Django รวมสิทธิ์จากทุก Group ของผู้ใช้
- data scope และ workflow เป็นเงื่อนไขเพิ่มเติมที่ authorization service ต้องตรวจแยก
- ดูความหมายเชิงธุรกิจที่ [Roles](/docs/roles) และรหัสสิทธิ์ที่
  [Permissions](/docs/roles/permissions)
- ดูคำอธิบายรายตารางและรายคอลัมน์ที่
  [Django Authentication Tables](/docs/database/django-auth) และ
  [Tenant & Authorization Tables](/docs/database/tenant-authorization)

## PostgreSQL Row-Level Security

ใช้ PostgreSQL Row-Level Security (RLS) เป็นชั้นป้องกันเพิ่มเติมสำหรับตาราง
ข้อมูลของ Workspace โดยไม่ใช้แทน Django permission หรือ Workspace filter

- เปิด RLS และกำหนด policy แบบ default deny สำหรับตารางข้อมูลของ Workspace
- ตรวจทั้งการอ่านและการเขียนด้วย `USING` และ `WITH CHECK`
- กำหนด Workspace context ฝั่ง server จาก Membership ที่ตรวจสอบแล้ว
- ค่า `app.tenant_id` เป็น internal `tenants.id` แบบ `BIGINT`; ห้ามนำ UUID จาก
  `X-Tenant-ID` ไปตั้ง context โดยตรง
- ใช้ transaction-scoped context เพื่อไม่ให้ค่าของ request หนึ่งค้างไปยัง
  connection ที่ request อื่นนำกลับมาใช้
- Application database role ต้องไม่เป็น table owner, superuser หรือมีสิทธิ์
  `BYPASSRLS`
- แยก migration/administration role ออกจาก application runtime role
- Background job, report และ command ต้องกำหนด Workspace context ก่อน query
- การทำงานข้าม Workspace ใช้เฉพาะ controlled service พร้อม approval และ audit

RLS เป็น defense in depth หาก application ลืมกรอง Workspace แต่ไม่สามารถแทน
กฎระดับ module, role, Matter, record scope หรือ approval state ได้

## Tenant Settings and Number Sequences

`GET/PATCH /api/settings` เป็น API façade ที่รวมข้อมูลจาก typed tables หลายตาราง
Frontend จึงไม่ต้องทราบ physical schema และ Backend สามารถตรวจชนิดข้อมูลกับสิทธิ์
ของแต่ละส่วนได้ชัดเจน

| ตาราง | หน้าที่ |
| --- | --- |
| `tenants` | ชื่อ, ชื่อตามกฎหมาย, Tax ID, locale, timezone และ lifecycle |
| `tenant_profiles` | อีเมลบริษัทและเว็บไซต์แบบ one-to-one กับ Tenant |
| `tenant_addresses` | ที่อยู่สำนักงาน แยกด้วย `(tenant_id, address_type)` |
| `tenant_number_sequences` | รูปแบบและ counter สำหรับเลข Client, Employee, Matter และ Quotation |
| `audit_events` | ประวัติการเปลี่ยนค่าที่เพิ่มได้อย่างเดียวและแก้ย้อนหลังไม่ได้ |

ไม่ใช้ universal JSONB หรือ key-value settings table สำหรับค่าที่รู้โครงสร้างแล้ว
เพราะจะทำให้ database บังคับ type, length, uniqueness และ foreign key ได้ยาก
JSONB สงวนไว้สำหรับ integration/plugin metadata ที่โครงสร้างไม่แน่นอนจริงเท่านั้น

แต่ละ Tenant ต้อง provision sequence ต่อไปนี้ โดยเริ่ม `next_number = 1`:

| `sequence_key` | Prefix | Padding |
| --- | ---: | ---: |
| `client` | `CUS-` | 5 |
| `employee` | `EMP-` | 5 |
| `matter` | `MAT-` | 5 |
| `quotation` | `QT-` | 5 |

เลขที่แสดงคำนวณด้วย `prefix || lpad(number::text, padding, '0')` เช่น
`MAT-00001` Prefix ต้องยาว 1–20 ตัวอักษร และ padding ต้องเป็นจำนวนเต็ม 1–12
API ไม่รับหรือส่ง `nextNumber`; client แก้ได้เฉพาะ prefix และ padding

Backend ต้องจองเลขแบบ atomic ภายใน transaction ด้วย `UPDATE ... RETURNING`
ห้ามอ่าน counter แล้วค่อย update แยกคำสั่ง เพราะ concurrent request อาจได้เลขซ้ำกัน
เลขไม่ reset และยอมให้มี gap เมื่อ transaction ภายหลังยกเลิกหรือ business record ถูก
ยกเลิก แต่ห้ามนำเลขเดิมกลับมาใช้ การเปลี่ยน prefix/padding มีผลเฉพาะเลขที่ออกใหม่
และต้องสร้าง `audit_events` ที่เก็บค่าเดิม ค่าใหม่ ผู้แก้ และเวลา Companion migration
ติดตั้ง trigger ห้ามลด `next_number` เพื่อป้องกัน reset/reuse แม้ application ทำงานผิดพลาด

## Tenant Lifecycle and Deletion Safety

การหยุดใช้ Workspace ตาม flow ปกติต้องเปลี่ยน `tenants.status` เป็น `archived`
และบันทึก `archived_at` โดยไม่ลบข้อมูลลูก ความสัมพันธ์ หรือ Audit Log ผู้ดูแล
สามารถระงับชั่วคราวด้วย `suspended` และนำ Workspace ที่เก็บถาวรกลับมาใช้ได้
ตาม policy ที่ได้รับอนุมัติ

- Foreign Key ทุกเส้นที่อ้าง `tenants.id` ต้องใช้ `ON DELETE RESTRICT` หรือ
  `NO ACTION`; ห้ามใช้ `CASCADE` หรือ `SET NULL`
- Backend ต้องปฏิเสธการเลือก Workspace ที่ `status = 'archived'` และห้ามตั้ง
  `app.tenant_id` สำหรับ request หรือ background job ของ Workspace นั้น
- การลบจริงอนุญาตเฉพาะ Tenant ที่สร้างผิดและยังไม่มี Membership, Subscription
  หรือข้อมูลอื่นอ้างอิง จึงไม่ทำให้ข้อมูลธุรกิจสูญหาย
- Phase 0 ยังไม่มี controlled purge ผู้ดูแลระบบจึงห้ามลบ Tenant ที่เคยใช้งาน
- กระบวนการ purge ในอนาคตต้องกำหนดผู้อนุมัติ ระยะรอ การส่งออกข้อมูล Backup,
  Audit Log, retention และ Legal Hold ก่อนเปิดใช้งาน

## Employee Organization Data

`departments` และ `job_positions` เป็น master data แยกตาม Tenant ส่วน
`employees` เก็บ `department_id`, `job_position_id` และ
`manager_employee_id` เป็น internal `BIGINT` references ห้ามเก็บชื่อแผนกหรือ
ตำแหน่งซ้ำบน Employee record

- Department และ Position ใช้ stable code ที่ไม่ซ้ำแบบ case-insensitive ภายใน Tenant
- Position ไม่ผูกกับ Department เดียว เพื่อให้ตำแหน่งเดียวกันใช้ได้หลายทีม
- การสร้างหรือย้าย Employee เลือกได้เฉพาะ catalog record ที่ active
- การ archive catalog ไม่ทำลาย Employee เดิม แต่ห้ามใช้กับ assignment ใหม่
- Manager และ parent Department ต้องอยู่ Tenant เดียวกันและห้ามเกิดวงจร
- การลบ Department หรือ Position ที่ถูกใช้งานต้องถูก Foreign Key ปฏิเสธ

API Employee ยังคงใช้ `department` และ `position` เป็น stable code เพื่อรักษา
frontend contract ส่วน Backend resolve code เป็น internal ID ภายใต้ Tenant context
ก่อนบันทึก การเพิ่มหรือเปลี่ยนชื่อ catalog ผ่านหน้า Administration เป็นงานภายหลัง

Migration ที่มีข้อมูลเดิมต้องสร้าง catalog จากค่าที่ normalize แยกตาม Tenant,
เพิ่ม FK แบบ nullable, backfill และตรวจค่าที่ map ไม่ได้ก่อน validate composite FK
จากนั้นจึงเปลี่ยน FK เป็น `NOT NULL` และลบ text columns เดิม ห้ามเลือก fallback
department หรือ position ให้ข้อมูลที่กำกวมโดยอัตโนมัติ

## Effective-Dated Employment History

`employee_employment_versions` เป็น source of truth ของแผนก ตำแหน่ง หัวหน้างาน
ประเภทการจ้าง และช่วงสัญญาตาม effective date ส่วน `employees` เก็บ
`current_employment_version_id` และ current snapshot เพื่อให้ API เดิมกับ query
หน้ารายชื่อทำงานได้รวดเร็ว ค่า snapshot ทุกช่องต้องตรงกับ version ที่เลือก

Backend คำนวณ business date จาก `tenants.timezone` แล้วเลือก active version ล่าสุด
ที่ `effective_from <= business_date` หากยังไม่มี version ที่เริ่มใช้ ให้เลือก future
version แรกตามแนวทาง Odoo 19 `hr.version` สถานะ past/current/future และวันสิ้นสุด
ของ version เป็นค่าที่ derive ไม่เก็บเป็น column ส่วน As-of report ต้องอ่านจาก history
โดยตรง ไม่อ่าน current snapshot

- การสร้าง แก้ หรือ void version ต้อง lock Employee ด้วย
  `SELECT id FROM employees WHERE tenant_id = :tenant_id AND id = :employee_id FOR UPDATE`
- การเปลี่ยน version กับ current snapshot ต้องอยู่ transaction เดียวกัน
- Daily idempotent job refresh รายการที่ future version เริ่มมีผล
- Read/write service ต้อง lazy-refresh ด้วย จึงไม่พึ่ง scheduler เพียงอย่างเดียว
- Runtime role ห้าม hard delete history; การแก้ไขใช้ `is_active=false`, version ใหม่
  และ append-only `audit_events`
- Employee ที่มี history ต้อง archive แทน hard delete และยังคง current pointer ไว้
- Department, Position, Manager และผู้บันทึกที่ history อ้างถึงต้องถูก FK ปฏิเสธ
  การ hard delete เพื่อรักษาความหมายของข้อมูลย้อนหลัง
- Current reporting line ถูกตรวจวงจรด้วย deferred database trigger ส่วน future
  hierarchy ต้องตรวจใน Django ทั้งตอนสร้างและตอน activate
- Contract date checks ต้องติดตั้งเป็น named table constraints ใน companion migration
  เพราะ drawDB แสดง check บน `DATE` ได้แต่ PostgreSQL exporter ไม่ส่ง check นี้ออกมา

Migration สำหรับข้อมูลเดิมต้องทำตามลำดับต่อไปนี้:

1. เพิ่ม history table และ pointer/current snapshot fields แบบ nullable
2. สร้าง active initial version ต่อ Employee โดยใช้ `employment_start_date`
3. หากไม่มีวันเริ่มงาน ให้ใช้วันสร้าง Employee ตาม timezone ของ Tenant และรายงานทุก
   record ที่ใช้ fallback เพื่อให้ผู้ดูแลตรวจสอบ
4. กรณีหา actor เดิมไม่ได้ ให้ใช้ system/provisioning tenant membership ที่กำหนดไว้
5. Backfill pointer และ current snapshot ด้วย effective-date selector
6. ตรวจ composite foreign keys, partial uniqueness, contract dates และจำนวนข้อมูล
   แยกตาม Tenant
7. เปิด deferred snapshot triggers และ RLS หลัง validation สำเร็จเท่านั้น

## PostgreSQL Partitioning

ใช้ Declarative Partitioning เฉพาะตารางที่มีขนาดใหญ่และมีรูปแบบ query หรือ
retention ที่ได้ประโยชน์จาก partition pruning ไม่แบ่ง partition
ทุกตารางตั้งแต่ต้น

ตารางที่ควรเตรียมรองรับ:

- Audit Log และ Access Event
- Notification Delivery Event
- Integration/Webhook Event
- Background Job History
- ตาราง transaction หรือ time-series อื่นเมื่อมีผลวัดรองรับ

แนวทางออกแบบ:

- เริ่มจาก `RANGE` partition ตามเวลา เช่น รายเดือนหรือรายไตรมาส
- ไม่สร้างหนึ่ง partition ต่อหนึ่ง Workspace เพราะจำนวน partition จะเพิ่มตาม
  จำนวนบริษัท
- Query ยังต้องมี `workspace_id`; partitioning ไม่ใช่การแยกข้อมูล tenant
- Index ของแต่ละ partition ต้องรองรับ `workspace_id`, เวลา สถานะ และรูปแบบ query
  ที่ใช้งานจริง
- ตรวจผลของ partition key ต่อ primary key, unique constraint และ foreign key
  ก่อน migration
- สร้าง partition ล่วงหน้าและแจ้งเตือนเมื่อไม่มี partition รองรับข้อมูลใหม่
- การ detach หรือ delete partition ต้องผ่าน retention, Legal Hold และ approval
- เปิดใช้หลังตรวจขนาดตาราง query plan, latency, write pattern และ restore
  process

## Indexing and Query Performance

- สร้าง composite index โดยเริ่มจาก `workspace_id` สำหรับ query ที่ใช้บ่อย
- เพิ่ม index ตาม filter, ordering และ join ที่พบจาก query จริง
- ไม่สร้าง index ทุก column เพราะเพิ่มพื้นที่และต้นทุนในการเขียนข้อมูล
- ใช้ `EXPLAIN (ANALYZE, BUFFERS)` ใน staging กับข้อมูลที่มีขนาดใกล้เคียงจริง
- ตรวจ slow query, connection usage, lock, dead tuple และ index usage ผ่าน
  monitoring

## Backup and Recovery

- เปิด automated backup และ point-in-time recovery ของ Cloud SQL
- กำหนด retention ตามประเภทข้อมูล สัญญา และ Legal Hold
- ป้องกันการลบ production database โดยไม่ตั้งใจ
- ใช้ versioning/lifecycle ที่เหมาะสมกับไฟล์ใน Cloud Storage
- ทดสอบ restore ลง isolated environment และตรวจทั้ง schema, row count,
  relationship, file linkage และ Workspace isolation
- Backup ที่ไม่เคยผ่าน restore test ยังไม่ถือว่าใช้กู้คืนได้

## Required Database Tests

- Workspace A อ่าน สร้าง แก้ไข หรือลบข้อมูล Workspace B ไม่ได้
- การเปลี่ยน `workspace_id` ใน request ไม่เปลี่ยนขอบเขตข้อมูล
- RLS ปฏิเสธ query เมื่อไม่มี Workspace context หรือ context ไม่ตรง
- `INSERT` และ `UPDATE` ไม่สามารถย้ายข้อมูลไป Workspace อื่น
- Application role ไม่สามารถ bypass RLS
- Backend ต้องปฏิเสธ archived Workspace ก่อนสั่ง `SET LOCAL app.tenant_id`
- Background job และ report ไม่รวมข้อมูลข้าม Workspace
- มอบหมาย role ของ Workspace A ให้สมาชิกของ Workspace B ไม่ได้
- การลบ Workspace ที่มีสมาชิก role, subscription หรือข้อมูลธุรกิจต้องถูก
  Foreign Key ปฏิเสธ
- การ archive Workspace ต้องเก็บ role, role assignment และ Audit Log ไว้ครบถ้วน
- Sequence key ซ้ำใน Workspace เดียวกัน Prefix/counter/padding ที่ผิดเงื่อนไข
  และการแก้ Audit Event ต้องถูก PostgreSQL ปฏิเสธ
- Concurrent allocator ต้องคืน running number ไม่ซ้ำ และ format ที่เปลี่ยนต้องไม่
  แก้เลขที่ออกไปแล้ว
- Department, Position และ Manager ที่อ้างจาก Employee ต้องอยู่ Workspace เดียวกัน
  และ PostgreSQL ต้องปฏิเสธ hierarchy cycle กับ normalized code ที่ซ้ำ
- Partition routing และ partition pruning ทำงานตามช่วงที่กำหนด
- การสร้าง partition ใหม่ไม่ทำให้ constraint หรือ index หาย
- Restore test รักษาข้อมูล ความสัมพันธ์ audit history และขอบเขต Workspace
